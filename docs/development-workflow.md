# Question Scan 开发工作流

这份文档定义了 Question Scan 的固定开发流程。以后只要是在这个仓库里做产品工作、代码修改、测试、打包、发布准备，默认都按这套流程走。

## 资料来源

- PRD：`prd/prd-question-scan.md`
- 任务清单：`tasks/tasks-question-scan.md`
- 代理说明：`AGENTS.md`

PRD 定义产品范围。任务清单定义执行顺序。`AGENTS.md` 定义任何代理进入仓库后必须遵守的规则。

## 使用场景

### 场景 001：开始一次开发会话

作为开发者，我需要一个固定的进入流程，这样我每次都知道下一步该做什么。

验收条件：

- 先查看 `git status --short --branch`。
- 再读取 `tasks/tasks-question-scan.md` 里第一个未完成的子任务。
- 确认这项工作属于 PRD 范围。
- 一次只做一个子任务。
- 没有得到用户确认前，不进入下一个子任务。

### 场景 002：完成一个子任务

作为开发者，我需要每个小步骤都能及时记录，这样进度才可追踪。

验收条件：

- 完成当前子任务里最小且有效的改动。
- 运行这个子任务能覆盖到的最快验证。
- 把 `tasks/tasks-question-scan.md` 里对应子任务从 `[ ]` 改成 `[x]`。
- 如果文件有增删，更新 `相关文件`。
- 停下来，询问用户是否继续。

### 场景 003：完成一个父任务

作为开发者，我需要把父任务当成稳定检查点。

验收条件：

- 该父任务下的所有子任务都标记为 `[x]`。
- 运行完整可用的测试套件。
- 如果项目里存在 E2E 命令，就运行 E2E。
- 只有验证通过后，才能把父任务标记为 `[x]`。
- 用规范化提交信息提交。
- 提交成功后推送分支。

### 场景 004：项目还没有完整测试或 E2E 时的处理

作为开发者，我需要明确的规则，这样当项目还没有完整测试时不会乱做。

验收条件：

- 先运行能运行的验证命令。
- 如果没有自动化验证，就做手动验证，并把检查内容写清楚。
- 没有 E2E 命令时，不要声称 E2E 已通过。
- 在提交实现代码前，要么补上可行的验证，要么明确说明阻塞点。

### 场景 005：保持产品边界

作为项目维护者，我需要开发过程始终留在已批准的范围内。

验收条件：

- 产品只保留授权练习、自测、开放题目环境和个人工作流使用。
- 不新增隐蔽考试使用、监考规避、屏幕共享规避、自动第三方提交、自动填答案等能力。
- 任何会改变产品范围的新任务，必须先更新 PRD，再进入实现。

## 固定流程

### 1. 会话开始

先执行：

```bash
git status --short --branch
```

然后阅读：

```text
tasks/tasks-question-scan.md
prd/prd-question-scan.md
```

优先选择第一个未完成的子任务，除非用户明确指定了别的任务。

### 2. 子任务执行

一次只做一个子任务。

每个子任务都按这个顺序走：

- 先说明现在要做哪个子任务。
- 只查看这个子任务必须用到的文件。
- 用最小改动完成需求。
- 这个子任务改变了行为，就补测试或更新测试。
- 运行最快、最相关的验证。
- 更新 `tasks/tasks-question-scan.md`。
- 停下来，等用户确认再开始下一个子任务。

### 3. 父任务检查点

当某个父任务下的所有子任务都完成后：

1. 运行前端测试，如果前端已配置：

   ```bash
   npm test -- --run
   ```

2. 如果存在 Rust 代码，再运行 Rust 测试：

   ```bash
   cargo test
   ```

3. 如果项目里存在 E2E 命令，就运行 E2E。

4. 按父任务要求做手动验证。

5. 把父任务标记为 `[x]`。

6. 检查 diff：

   ```bash
   git diff --check
   git status --short
   ```

7. 只暂存和当前任务有关的文件。

8. 提交。

9. 推送分支。

### 4. 提交格式

提交时使用规范化提交，并带上任务上下文。

示例：

```bash
git commit -m "feat: add global shortcut workflow" -m "- Registers configurable Ctrl+Shift+Q shortcut" -m "- Adds tray actions and status states" -m "- Completes task 2.0 for Question Scan MVP"
```

建议使用的前缀：

- `feat:` 表示新功能。
- `fix:` 表示修复问题。
- `test:` 表示只改测试。
- `docs:` 表示只改文档。
- `chore:` 表示项目配置或维护。
- `refactor:` 表示行为不变的重构。

### 5. 推送规则

每完成一个并且已经提交的父任务，就推送一次。

推荐分支流程：

```bash
git checkout main
git pull origin main
git checkout -b feature/question-scan-mvp
```

`main` 用于稳定、已验证的工作。`feature/question-scan-mvp` 用于 MVP 开发。

### 6. 各阶段验证门槛

#### 任务 1.0：Tauri 应用底座

必须验证：

- `npm run tauri dev` 能启动应用。
- 如果前端测试已配置，前端测试能通过。
- 基础界面没有明显布局问题。

#### 任务 2.0：全局快捷键和托盘流程

必须验证：

- 快捷键设置能保存。
- 快捷键冲突能处理。
- 后台触发能手动验证。
- 托盘菜单能手动操作。

#### 任务 3.0：屏幕截图和临时图片链路

必须验证：

- 在 Windows 上能生成截图。
- 临时图片元数据正确。
- 成功和失败后都能清理临时图片。
- 裁剪坐标和无效路径的测试通过。

#### 任务 4.0：题目区域识别和手动框选兜底

必须验证：

- 在自动识别完成之前，手动框选必须先可用。
- AI 返回的坐标要和截图边界校验。
- 低置信度要进入手动框选。
- 浏览器、PDF、IDE、深色页面都要手动检查。

#### 任务 5.0：AI 服务配置和多模态请求

必须验证：

- 请求前能校验服务配置。
- OpenAI 风格的图片请求体格式正确。
- 流式和非流式路径都能测试。
- 至少手动验证一次真实图片请求。

#### 任务 6.0：直接输出算法解法

必须验证：

- 默认语言能用 C++17 或 C++20。
- Python、Java、JavaScript、TypeScript、Go、Rust 模板都存在。
- 主代码块提取正常。
- 至少手动验证数组、动态规划、图三个题型。

#### 任务 7.0：结果面板和输出速度

必须验证：

- Markdown 和代码块能正确渲染。
- 复制代码和复制完整答案拿到的是完整内容。
- 快速、正常、慢速和自定义展示速度都能工作。
- 长 C++ 输出不会把常见桌面布局撑坏。

#### 任务 8.0：设置、历史、缓存和隐私

必须验证：

- 设置重启后还能保留。
- 关闭历史后不会保存题目和答案。
- 默认不保存整张截图。
- 缓存清理能删掉遗留的临时图片。
- 隐私数据流有文档说明。

#### 任务 9.0：Windows MVP 打包

必须验证：

- Windows 安装包能构建成功。
- README 写清楚安装和使用流程。
- PRD 里的 MVP 验收条件做过手动检查。
- 发布前把已知限制写清楚。

## 范围边界

允许做的内容：

- 用户主动触发的截图。
- 本地裁剪和临时图片生成。
- 把用户确认过的截图或裁剪图发给已配置的 AI 服务。
- 面向授权练习和开放题目环境的直接算法解法输出。
- 用户可控的本地历史和缓存清理。

禁止做的内容：

- 隐蔽考试使用。
- 监考规避。
- 屏幕共享规避。
- 反监控行为。
- 自动提交到第三方平台。
- 自动把答案填进第三方网页。
- 读取浏览器 Cookie、账号、凭据或其他无关个人数据。

## 完成定义

一个任务只有在下面这些条件都满足时，才算完成：

- 需求已经实现，或者已经写进文档。
- 相关测试或手动验证已经运行。
- `tasks/tasks-question-scan.md` 已更新。
- `相关文件` 已经写对。
- 临时文件和调试代码都清理掉了。
- 父任务在所有子任务完成后已经提交并推送。
