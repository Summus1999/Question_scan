# PRD：Question Scan 桌面算法解题助手

## 1. 概述

Question Scan 是一个基于 Tauri 的桌面软件。用户按下全局快捷键后，软件截取当前屏幕，自动识别屏幕中的算法题区域，生成临时图片，并把图片和用户配置发送给多模态 AI。AI 返回题目分析、解题思路、主流语言代码、复杂度说明和边界条件。产品默认用于授权练习、自测、开放题目环境和个人效率场景。

这个产品的核心不是导师式教学，而是快速把屏幕上的算法题转换成可用答案。用户可以配置默认语言、输出速度、模型服务、结果格式和是否保存历史。

## 2. 产品目标

- 用户按下快捷键后，5 秒内完成屏幕截图和题目区域识别。
- 用户无需复制题目文本，也能从截图得到结构化题目内容。
- 用户可以选择 C++、Python、Java、JavaScript、TypeScript、Go、Rust 等主流语言生成答案。
- 用户可以配置结果面板的流式展示速度。真实生成速度由模型和网络决定，软件控制本地展示节奏。
- 用户可以把 AI 输出复制到剪贴板，保存到本地历史，或导出为代码文件。
- 软件只在用户主动触发时截图，并在请求完成后删除临时图片，除非用户选择保存历史。

## 3. 目标用户

- 正在准备算法笔试、机试和技术面试的开发者。
- 希望减少刷题检索、复制、整理时间的用户。
- 在开放练习环境中需要快速生成参考解法的人。
- 需要对同一道题生成多语言答案的人。

## 4. 核心用户流程

1. 用户打开软件，配置 AI Provider、API Key、默认模型、默认语言和输出速度。
2. 用户在浏览器、PDF、IDE 或题库页面中看到一道算法题。
3. 用户按下全局快捷键，例如 `Ctrl+Shift+Q`。
4. 软件截取所有显示器的当前画面。
5. 软件识别最可能的算法题区域，并生成裁剪后的临时图片。
6. 软件把临时图片、默认语言和输出格式要求发送给 AI。
7. AI 返回题目文本、解题思路、代码、复杂度和边界条件。
8. 软件在结果面板中按配置速度展示内容。
9. 用户复制代码、保存记录，或切换语言重新生成。

## 5. 功能需求

### 5.1 全局快捷键

FR-001：系统必须支持用户配置全局快捷键。

FR-002：系统必须在后台运行时响应快捷键。

FR-003：系统必须支持启用、禁用和重置快捷键。

FR-004：当快捷键和系统或其他应用冲突时，系统必须提示用户重新设置。

### 5.2 屏幕截图

FR-005：系统必须支持截取当前屏幕。

FR-006：系统必须支持多显示器截图。

FR-007：系统必须在截图前显示状态反馈，例如托盘图标变化或面板状态变化。

FR-008：系统必须在本地生成临时图片文件。

FR-009：系统必须在请求完成后删除临时图片，除非用户启用保存截图。

### 5.3 题目区域识别

FR-010：系统必须从全屏截图中定位最可能的算法题区域。

FR-011：系统必须支持题目区域自动裁剪。

FR-012：系统必须支持识别失败后的手动框选兜底方案。

FR-013：系统必须识别题目中的标题、描述、输入输出、示例、约束和函数签名。

FR-014：系统应支持中文题目和英文题目。

### 5.4 AI 请求与答案生成

FR-015：系统必须支持 OpenAI-compatible 的多模态模型接口。

FR-016：系统必须允许用户配置 API Base URL、API Key、模型名和请求超时时间。

FR-017：系统必须把裁剪后的临时图片作为主要输入发送给 AI。

FR-018：系统必须把默认语言、答案风格、输出格式和用户偏好一起发送给 AI。

FR-019：系统必须支持流式输出。

FR-020：系统必须在 AI 请求失败时展示明确错误信息，并允许重试。

### 5.5 直接解题输出

FR-021：系统必须输出可复制的完整代码。

FR-022：系统必须输出题目识别结果，便于用户确认 AI 是否看懂题目。

FR-023：系统必须输出核心算法思路，但不以教学对话为主要形态。

FR-024：系统必须输出时间复杂度和空间复杂度。

FR-025：系统必须输出边界条件和常见测试用例。

FR-026：系统必须支持一键切换语言并重新生成答案。

FR-027：系统必须支持 C++17 或 C++20 作为默认语言选项。

### 5.6 输出速度配置

FR-028：系统必须支持配置结果面板的展示速度。

FR-029：展示速度配置至少包含三档：快速、正常、慢速。

FR-030：系统应支持自定义字符每秒或代码块逐段展示。

FR-031：系统必须说明展示速度不等于模型生成速度。模型生成速度受 Provider、模型、网络和请求负载影响。

### 5.7 结果面板

FR-032：系统必须提供一个可固定、可收起的结果面板。

FR-033：结果面板必须展示请求状态：截图中、识别中、生成中、完成、失败。

FR-034：结果面板必须支持复制完整代码。

FR-035：结果面板必须支持复制完整答案。

FR-036：结果面板必须支持清空当前结果。

FR-037：结果面板应支持 Markdown 和代码高亮。

### 5.8 语言与模板

FR-038：系统必须支持配置默认编程语言。

FR-039：系统必须支持 C++、Python、Java、JavaScript、TypeScript、Go 和 Rust。

FR-040：系统应支持按语言配置代码风格，例如 C++ 使用 `#include <bits/stdc++.h>` 或标准头文件。

FR-041：系统应支持题目平台模板，例如 ACM 输入输出、LeetCode 函数签名、牛客输入输出。

### 5.9 本地历史

FR-042：系统应支持保存历史记录。

FR-043：历史记录应包含截图时间、题目识别文本、语言、AI 输出、用户备注和模型信息。

FR-044：系统必须允许用户关闭历史保存。

FR-045：系统必须允许用户删除单条历史和清空全部历史。

### 5.10 隐私与数据控制

FR-046：系统必须只在用户主动触发快捷键时截图。

FR-047：系统必须提示用户截图会发送给所配置的 AI 服务。

FR-048：系统必须避免默认保存完整屏幕截图。

FR-049：系统必须允许用户查看和删除本地缓存。

FR-050：系统必须在设置页展示数据流向：屏幕截图、本地裁剪、临时图片、AI 请求、结果保存。

## 6. 非目标范围

- 不做隐蔽用于真实面试、在线考试或受限评估的功能。
- 不做检测规避、屏幕共享规避、窗口隐藏规避或反监控能力。
- 不做自动提交到第三方题库平台。
- 不做自动填入第三方网页答案框。
- 不读取用户账号、Cookie、浏览器私密数据或第三方平台凭据。
- MVP 不做云同步、账号系统、支付系统和团队管理。
- MVP 不做完整本地判题系统。

## 7. 设计要求

- 主界面应以结果面板和设置为核心，不做复杂学习路径。
- 软件启动后进入托盘和简洁控制台。
- 状态反馈要清楚，用户能知道当前处于截图、识别、请求还是输出阶段。
- 代码区域要支持语法高亮、复制和折叠。
- 设置项要集中：快捷键、AI Provider、语言、输出速度、历史保存、隐私选项。
- 出错时要给出可执行建议，例如检查 API Key、模型是否支持图片、网络是否可用。

## 8. 技术方案建议

### 8.1 桌面框架

- Tauri 2.x
- Rust 后端
- React + TypeScript + Vite 前端
- Tailwind CSS
- shadcn/ui 或 Radix UI
- lucide-react 图标

### 8.2 Tauri 能力

- 使用全局快捷键插件监听用户触发。
- 使用 Rust 截图库捕获当前屏幕。
- 使用 `image` 类库完成裁剪、压缩和临时文件生成。
- 使用 Rust 后端发起 AI 请求，减少 API Key 暴露。
- 使用系统托盘承载后台运行状态。

### 8.3 题目定位方案

MVP 推荐两级方案：

- 自动方案：把全屏截图低清压缩后交给视觉模型，要求返回题目区域坐标和题目文本，再本地裁剪高清区域。
- 兜底方案：自动识别失败时，让用户手动框选题目区域。

后续版本可以加入本地 OCR，提高定位速度，减少 AI 调用成本。

### 8.4 AI Prompt 输出结构

AI 输出必须固定为以下结构：

```text
题目识别：
解题策略：
代码语言：
完整代码：
复杂度：
边界用例：
注意事项：
```

代码输出必须优先满足用户选择的语言和平台模板。

### 8.5 本地存储

- SQLite 保存设置和历史。
- 系统临时目录保存请求过程中的图片。
- 默认不保存完整截图。
- 用户开启历史时保存题目文本和答案。

## 9. 开发阶段规划

### 阶段 0：产品边界和技术验证，1-2 天

目标：验证 Tauri 是否能稳定完成全局快捷键、截图、临时图片和 AI 图片请求。

交付：

- 技术验证文档。
- 快捷键触发截图 Demo。
- 单张图片发送给 AI 并得到答案的 Demo。

### 阶段 1：Tauri 项目基础，2-3 天

目标：搭建可运行桌面应用。

交付：

- Tauri + React + TypeScript 项目。
- 托盘、主窗口、设置页骨架。
- 基础日志、错误提示和配置存储。

### 阶段 2：截图与题目识别，4-6 天

目标：完成快捷键触发后的全屏截图、题目区域识别和临时图片生成。

交付：

- 全局快捷键配置。
- 多显示器截图。
- 自动题目定位。
- 手动框选兜底。
- 临时图片生命周期管理。

### 阶段 3：AI 生成答案，4-6 天

目标：完成图片请求、多语言答案生成和结果展示。

交付：

- OpenAI-compatible API 配置。
- 多模态图片请求。
- C++、Python、Java、JavaScript、TypeScript、Go、Rust 输出模板。
- 流式输出。
- 请求失败重试。

### 阶段 4：输出面板与配置项，3-5 天

目标：让用户可控地查看、复制和调整答案。

交付：

- 可固定结果面板。
- 代码高亮。
- 一键复制代码和完整答案。
- 输出速度配置。
- 默认语言和平台模板配置。

### 阶段 5：历史、隐私和打包，3-5 天

目标：让软件可长期使用和发布。

交付：

- 本地历史记录。
- 缓存清理。
- 隐私设置。
- Windows 安装包。
- README 和使用说明。

## 10. MVP 验收标准

- 用户可以配置 API Key、模型、语言和快捷键。
- 用户按下快捷键后，软件可以截取屏幕并生成临时图片。
- 软件可以识别屏幕中的算法题区域，识别失败时允许手动框选。
- 软件可以把临时图片发送给 AI 并获得结构化答案。
- 用户可以选择 C++ 并得到可复制的完整代码。
- 用户可以配置结果展示速度。
- 软件默认不保存完整截图。
- 软件重启后保留用户设置。

## 11. 风险和应对

- 风险：全屏截图包含隐私信息。应对：只在用户主动触发时截图，默认不保存完整截图，设置页展示数据流向。
- 风险：题目区域识别不准。应对：先做手动框选兜底，再优化自动定位。
- 风险：不同 AI 模型对图片理解能力差异大。应对：设置页标注模型要求，错误信息提示模型需要支持图片输入。
- 风险：生成代码不能通过所有用例。应对：输出边界用例，并在后续版本加入本地样例运行。
- 风险：跨平台截图权限不同。应对：MVP 先以 Windows 为主，后续扩展 macOS 和 Linux。

## 12. 开放问题

- 第一版是否只支持 Windows？
- 默认 AI Provider 是 OpenAI-compatible，还是要优先兼容 Ollama、Gemini、Claude 等服务？
- 是否需要支持本地 OCR？
- 是否需要内置代码运行器，还是只输出答案？
- 历史记录是否默认开启？
